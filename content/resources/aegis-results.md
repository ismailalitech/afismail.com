Last updated 2026-11-21: repository releases [v1.0.0](https://github.com/ismailalitech/aegis/releases/tag/v1.0.0) and [v1.1.0](https://github.com/ismailalitech/aegis/releases/tag/v1.1.0) (the Prover SDK on every endpoint, transcript v2, endorsed enrolment, standard evidence and signed results, the signed audit log and policy, the 3-hour soak); before them [v0.2.0](https://github.com/ismailalitech/aegis/releases/tag/v0.2.0) and the main branch after it (the NXP RW612 and Zynq UltraScale+ endpoints, the STM32 fixes and probes, the stack mark in the STM32 heartbeat, the session's end on the endpoint, the gateway's watchdog, the bench watcher). Aegis 1.2 ([pull request 53](https://github.com/ismailalitech/aegis/pull/53), v1.2.0 being released) is in rows N1 and N2. Evidence classes: **SIM** (simulation), **HOST** (a check on a PC), **BUILD** (tool output) and **BOARD** (measured on the physical boards). A result is claimed only in the class that produced it. Raw records that are small enough to publish are in [`evidence/`](https://github.com/ismailalitech/aegis/tree/main/evidence) of the repository (`console/`, `endorsed-enrolment/`, `endpoint-expiry/`, `rw612-tfm/`, `sdk-core/`, `soak-20261121/`, `stm32-kemfix/`, `stm32-sstack/`, `stm32-tz/`, `transcript-v2/`, `zynqmp/`); the figures in this page that come from Libero are screenshots, listed in [`docs/figures/`](https://github.com/ismailalitech/aegis/tree/main/docs/figures).

The whole-system check is `tools/regression.sh --board`: thirteen stages, five on the PC and eight on the boards. With `--with-expiry` it adds a fourteenth, `endpoint-expiry`, off by default because it stops the fleet service for a few minutes. The five PC stages and the enforcement test also run on every push in GitHub Actions on a clean machine.

## 3. Limits

- **No network enforcement on the real gateway.** One Ethernet port and a processor USB controller that is not routed to a connector mean a managed 802.1Q switch is needed. The rules and the one-port VLAN design are tested in network namespaces; the placement is not.
- **The gateway's key is software.** The chip is the part without the data-security block.
- **Development keys on the endpoints.** The STM32s are in the open product state and the attestation key of TF-M is a published one; only the ML-DSA signature is security-relevant. The RW612 has no secure boot fused, so a secure image reflashed with a debugger can use the chip's key.
- **TF-M isolation:** level 1 on the STM32, level 2 on the RW612, where the Aegis partition shares privileged memory with TF-M's other PSA-RoT services.
- **The Zynq UltraScale+ key is partly tested.** The public key that checks the image's signature is in the boot header, not in fuses, so the boot ROM does not check who signed it; Linux is not yet kept away from the device key (phase C, prepared in the repository, not on the board); the kernel is not among the measurements; the design's tests 3 to 5 (non-secure probes, an unencrypted FSBL naming the black key, tampered images) are not done.
- **Enrolment.** The endpoints' keys are endorsed at the bench since 20 November 2026, by an endorser whose key is sealed to the bench PC's TPM; the gateway's own enrolment on the PC is trust on first use.
- **Root on the gateway** holds the verifier's key: it can write the audit log again (an anchor kept on the PC shows it), leave entries out as they happen, and replace the policy signers file.
- **EAR and AR4SI are IETF drafts,** and standard evidence runs on STM32 board 2 only.
- **The soak ran 3 hours,** not a day.
- **The endpoints have no wall clock.** A session ends after its length on the endpoint's own clock. The STM32's RTC runs on an RC oscillator measured 6 % slow on both boards, so an hour's session ends there after about 68 minutes; a debugger can stop any endpoint's clock. On the Zynq UltraScale+ the session's end is in trusted application 0.2.0 and tested on the PC only.
- **Two STM32 chips,** so per-chip uniqueness of the device key is shown on two chips, not on a population.
- **Not evaluated:** side channels, fault injection, power loss during provisioning. ML-DSA signing is hedged since lab 55; that it is hedged is shown on the PC, not observable on the board (each quote's PSA token differs anyway).
- Latency figures are two runs per setup, with the gateway services running and no heavy network or SD traffic.
- Everything was measured on one set of boards.
